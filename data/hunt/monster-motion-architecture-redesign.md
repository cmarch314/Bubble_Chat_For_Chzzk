# 몬스터 모션 구조 재설계안

## 왜 지금 구조로는 200마리를 못 하는가

숫자부터. 몬스터 9마리를 구현한 현재:

| 항목 | 수량 |
|---|---|
| `hunt-runtime.css` | 7,700줄 |
| `monster-motion-*` 키프레임 | 68개 |
| 키프레임 안의 px 리터럴 | 386개 |
| 좌표 배율 리터럴(`*.88` 등) | 264개 |
| 각도 리터럴 | 408개 |
| **손으로 맞춰야 하는 숫자 합계** | **1,058개** |

마리당 약 118개. 200마리면 **23,000개**를 손으로 맞춰야 한다. 이건 양의 문제가
아니라 종류의 문제다. 아래 네 가지가 구조적 원인이고, 이번 세션에서 넷 다 실제로
사고를 냈다.

### 원인 1 — 위치와 자세를 같은 요소가 갖는다

지금은 `.hunt-monster-attack-motion` 하나가 `translate`, `rotate`, `scale`을 전부
갖는다. 그래서 **회전이 위치를 바꾼다.**

가시 꼬리 내려찍기가 그 예다. "꼬리로 내려찍는다"를 표현하려고 회전축을 꼬리 끝
(`20% 12%`)에 뒀더니, 축과 몸통 중심 사이가 184px이라 180도 회전에서 몸통이
**지름 368px 호**를 그렸다. 이미지 크기가 380px이니 몸 전체가 원을 그리며 도는
그림이 된다.

회전축을 옮겨서 풀 수 있는 문제가 아니다. 축이 몸 밖에 있으면 몸이 돌고, 축이
몸 안에 있으면 꼬리가 제자리에 안 온다. **컨테이너 회전으로는 "몸은 두고 꼬리만
휘두르기"를 표현할 수 없다.**

### 원인 2 — 좌표가 리터럴이다

```css
73.3%{transform:translate(var(--narga-hit-x),var(--narga-hit-y))
      rotate(calc(var(--narga-aim-deg,0deg) + 180deg)) scale(1.10,1.52)}
```

`--narga-hit-x`는 `calc(var(--monster-attack-x)*var(--narga-standoff))`이고,
`--monster-attack-x`는 JS가 `dx * 0.92`를 클램프해 넣은 값이다. 즉 한 좌표를 알려면
**CSS 변수 3단계와 JS 클램프 2개**를 따라가야 한다.

이번 세션에서 "1번을 노렸는데 우측 상단을 때린다"의 원인이 정확히 이것이었다.
`approachX .92`와 `standoff .88`이 곱해져 표적까지의 81%에서 멈췄다. 두 배율이
서로 다른 파일에 있어서 아무도 곱셈을 못 봤다.

### 원인 3 — 특이도 사고가 조용히 일어난다

```css
.hunt-monster-attack-motion[data-monster-rig="winged"] { transform-origin:50% 54%; }  /* (0,2,0) */
.monster-motion-나르가-회전 { transform-origin:20% 88%; }                              /* (0,1,0) */
```

rig 기본이 이긴다. **모션별 회전축이 한 번도 적용된 적이 없었다.** 22개 규칙이
전부 그랬다. CSS는 오류를 내지 않으므로 검수에서 "안 고쳐졌다"로만 보인다.
같은 부류로 `calc(50% - -1*30%)` 문법 오류도 있었다 — 선언 하나가 통째로 무효화되고
아무 경고도 없다.

### 원인 4 — 타격 시점과 그림이 따로 논다

`impactTimeline`은 틱으로, 애니메이션은 퍼센트로 적는다. 둘을 사람이 맞춘다.
어긋나면 "때리는 순간과 소리가 다르다"로 나타난다. 실제로 `VISUAL_DURATION_SCALE`
이중 적용 때문에 모든 패턴이 25%씩 잘려 있었고, `recovery` 틱은 점유 시간 계산에
아예 반영되지 않아 3초 후딜이 화면에 없었다.

## 설계

### 원칙 1 — 레이어마다 하나의 책임

```
placement   translate 전용. 절대 회전·신축하지 않는다.
  └ pose    rotate/scale 전용. 절대 이동하지 않는다.
      └ part  부위별 신축(꼬리 늘이기 등). 이미지 위 오버레이.
          └ image
```

`placement`가 회전하지 않으므로 **좌표가 회전에 오염되지 않는다.** 원인 1이 구조적으로
사라진다. "몸은 두고 꼬리만" 같은 표현은 `part` 레이어가 담당한다 — 컨테이너가
아니라 꼬리 스프라이트만 늘이고 돌린다.

### 원칙 2 — 좌표는 이름으로 지정한다

런타임이 실제 레이아웃에서 해석하는 앵커 어휘를 둔다.

```js
'home'                      기본 위치
'hunter:2'                  2번 헌터 중심
'hunter:2.bottom'           2번 헌터 하단   (.top .left .right .center)
'between:1,2'               1번과 2번 사이
'above:hunter:2 +150'       2번 헌터 위 150px
'offscreen:left'            화면 밖 좌측
'polar:hunter:2 225deg 320' 2번 헌터 기준 225도 방향 320px
```

패턴 저작자는 `to: 'hunter:2.bottom'`이라고 쓴다. `calc(var(--monster-attack-x)*.88 + 114px)`
을 쓰지 않는다. **배율과 클램프는 앵커 해석기 한 곳에만 존재한다.**

앵커는 실측 기반이므로 레이아웃이 바뀌어도 따라간다. 지금처럼 `430` 클램프와 실제
거리 `505`의 차이를 `--narga-drop:75px`로 메우는 일이 없어진다.

### 원칙 3 — 모션은 비트(beat)의 조합이다

키프레임을 손으로 쓰지 않는다. 패턴이 비트 목록을 선언하면 런타임이 Web Animations
키프레임으로 컴파일한다.

```js
motion: [
  { beat: 'windup',  ticks: 5, pose: 'crouch' },
  { beat: 'leap',    ticks: 3, to: 'offscreen:left', pose: 'stretch' },
  { beat: 'appear',  ticks: 2, at: 'polar:hunter:2 225deg 700', face: 'hunter:2', fade: 'in' },
  { beat: 'strike',  ticks: 4, to: 'hunter:2.bottom', pose: 'lunge', hit: true, sfx: 'impact' },
  { beat: 'hold',    ticks: 2, pose: 'landed' },
  { beat: 'exit',    ticks: 3, to: 'polar:hunter:2 45deg 700', fade: 'out' },
  { beat: 'recover', ticks: 30, pose: 'tail-stuck' },
  { beat: 'return',  ticks: 4, to: 'home', pose: 'idle' }
]
```

여기서 자동으로 따라오는 것들:

- **총 길이** = 비트 틱 합. 애니메이션 길이가 틱에서 파생되므로
  `VISUAL_DURATION_SCALE` 이중 적용 같은 사고가 불가능하다.
- **타격 시점** = `hit: true`인 비트의 시작 틱. `impactTimeline`을 따로 적지 않는다.
  그림과 판정이 같은 곳에서 나오므로 어긋날 수 없다(원인 4 해소).
- **음향 시점** = `sfx`가 달린 비트. 선딜/타격/후딜 어디든 붙일 수 있다.
- **후딜** = `recover` 비트. 지금처럼 `recovery` 틱이 무시되는 일이 없다.
- **배속** = 비트의 틱 수에만 곱한다. 비율이 보존되므로 분노·아종·밸런싱 배율이
  그림을 깨지 않는다(`monster-timing-unification-plan.md`의 결론과 같다).

`pose`는 이름 붙은 자세 프리셋이다(`crouch` `stretch` `lunge` `landed` `spin-left` …).
자세는 몬스터 골격별로 한 번만 정의하고 모든 패턴이 재사용한다. 지금처럼 패턴마다
`scale(1.10,1.52)`를 손으로 적지 않는다.

### 원칙 4 — 회전은 부위에 건다

`pose`가 회전을 가질 때 축은 **골격 데이터의 부위 앵커**로 지정한다.

```js
{ pose: 'tail-slam', rotate: 180, pivot: 'part:tail-base', stretch: { part: 'tail', y: 1.5 } }
```

`part:tail-base`는 `HuntMonsterAnatomyCatalog`가 이미 갖고 있는 부위 좌표다.
CSS `transform-origin`을 직접 쓰지 않으므로 특이도 사고(원인 3)가 원천적으로
발생하지 않는다. 회전축은 CSS가 아니라 데이터다.

---

## 이렇게 하면 무엇이 달라지는가

**저작량.** 패턴 하나가 비트 6~8줄이다. 지금은 키프레임 15~35줄 + CSS 클래스 +
geometry 핸들러 + 프로필 데이터 네 곳을 고쳐야 한다. 마리당 118개 숫자가 20개 안팎의
이름으로 바뀐다.

**검수 왕복.** 지금은 숫자를 바꾸고 → 커밋하고 → 사용자가 새로고침하고 → 어긋나면
다시. 비트 구조에서는 검수 페이지가 비트 목록을 그대로 편집기로 띄울 수 있다.
앵커는 화면에 점으로 찍어 보여줄 수 있다. **숫자를 말로 주고받는 왕복이 없어진다.**

**토큰.** 이번 세션에서 모션 하나 고치는 데 평균 왕복 3회를 썼다. 원인은 대부분
"어디가 틀렸는지 화면 없이는 모른다"였다. 비트는 텍스트로 검증 가능하다 —
타격 비트가 있는지, 앵커 이름이 유효한지, 틱 합이 맞는지 전부 테스트로 잡힌다.

**사고 예방.** 원인 1~4가 각각 구조적으로 불가능해진다. 지금은 넷 다 "조용히 틀리는"
종류였고 그래서 비쌌다.

## 마이그레이션

기존 68개 키프레임을 한 번에 버리지 않는다. 새 시스템과 병존시킨다.

**1단계 — 앵커 해석기.** ✅ 완료. `HuntStageAnchors`가 좌표 어휘와 경계를 단독으로
소유한다. 아래 "1단계 결과"에 실제로 무엇이 바뀌고 무엇이 드러났는지 적었다.

**2단계 — 레이어 분리.** ✅ 완료. `pose` 레이어를 넣고 기존 모션은 `placement`에
그대로 뒀다. 아래 "2단계 결과" 참고.

**3단계 — 비트 컴파일러.** `HuntMotionCompiler`가 비트 목록을 Web Animations
키프레임으로 만든다. `motion` 필드를 가진 패턴만 새 경로를 탄다.

**4단계 — 나르가쿠르가부터 이전.** 가장 복잡하고 가장 많이 고친 몬스터다.
15개 패턴이 새 경로에서 재현되면 설계가 검증된 것이다.

**5단계 — 나머지 이전 후 옛 경로 제거.** 이전이 끝난 몬스터의 키프레임을 지운다.

각 단계는 독립적으로 배포 가능하고, 어느 단계에서 멈춰도 기존 몬스터는 동작한다.

---

## 지금 당장의 판단이 필요한 것

- **200마리 목표가 확정이면 1~3단계를 먼저 하는 게 싸다.** 나르가를 지금 방식으로
  더 다듬는 비용이, 새 구조로 옮기는 비용을 이미 넘어섰다.
- **1~2단계만 해도 이번 세션 사고의 대부분이 막힌다.** 좌표 오염과 특이도 사고가
  없어진다. 비트 컴파일러는 그다음이어도 된다.
- 파일 규모상 `hunt-runtime.css` 7,700줄은 이미 한 사람이 들고 있기 어렵다.
  몬스터별 분리도 함께 검토할 값어치가 있다.

# 부위(part)와 좌우 반전

## 부위 좌표는 데이터로 받는다

몬스터마다 머리·날개·앞발·꼬리 위치가 다르다. 이걸 매번 CSS 퍼센트로 추측하는 것이
이번 세션 사고의 절반이었다(꼬리 끝을 `20% 12%`로 추정했다가 몸통이 원을 그렸다).

부위 좌표를 몬스터 데이터로 받는다. **항상 뒤집지 않은 원본 이미지 기준**이고,
이미지 크기와 무관하도록 퍼센트로 적는다.

```js
nargacuga: {
  parts: {
    head:        { x: 50, y: 88 },                 // 점 앵커
    eyes:        [{ x: 44, y: 84 }, { x: 56, y: 84 }],
    'front-leg-left':  { x: 18, y: 86 },
    'front-leg-right': { x: 82, y: 86 },
    wing:        { x: 50, y: 60 },
    tail: {
      base: { x: 74, y: 22 },                      // 몸통과 이어지는 곳
      tip:  { x: 20, y: 12 },                      // 끝
    }
  }
}
```

- `점 앵커`는 회전축·투사체 출발점·이펙트 부착점으로 쓴다.
- 좌표는 대략이면 된다. 정확한 외곽선은 필요 없다.

## 부위는 점 앵커만 갖는다

부위별 이미지를 따로 만들거나 폴리곤으로 잘라내지 않는다. 200마리 x 5부위 =
1,000장을 그리는 것도, 외곽선을 손으로 따는 것도 규모가 맞지 않는다.

부위는 **대략적인 점 하나**다. 그 점으로 하는 일은 셋이다.

1. **회전축** — 꼬리 밑동을 축으로 돌면 꼬리가 휘두르는 그림이 된다.
2. **이펙트 부착점** — 투사체 출발, 부위 파괴 연출, 상태 표시.
3. **신축 기준** — 그 점을 고정한 채 이미지를 늘이면 그 방향으로 뻗는 느낌이 난다.

부위만 정확히 떼어내는 것은 포기한다. 몸이 함께 늘어나는 것은 근사로 받아들이고,
대신 **필터와 노이즈로 그 부위에 시선을 모은다.**

```js
{ pose: 'tail-slam',
  pivot: 'part:tail.base',        // 꼬리 밑동을 축으로
  rotate: 180,
  scale: [1.10, 1.52],            // 축 방향으로 늘어난다
  accent: { at: 'part:tail.tip', fx: 'impact-glow' } }   // 시선을 꼬리 끝에
```

이 선택은 이전 인터뷰에서 이미 합의했다("회전·신축으로 근사"). 여기서 달라지는
것은 **회전이 위치를 오염시키지 않는다는 점**이다. placement 레이어가 돌지 않으므로
근사가 어긋나도 좌표는 멀쩡하다. 지금은 근사가 어긋나면 좌표까지 같이 무너졌다.

## 좌우 반전 — 규칙 세 개

반전은 조용히 망가진다. `scaleX(-1)` 안에서는 회전이 반대로 보이고, 부위 좌표가
좌우로 바뀌며, 이동 방향이 두 번 뒤집히기도 한다. 규칙으로 못박는다.

### 규칙 1 — 반전은 가장 안쪽 레이어에만 건다

```
placement   translate            (반전 영향 없음)
  └ pose    rotate / scale       (월드 좌표계. 반전 영향 없음)
      └ facing  scaleX(±1)       ← 반전은 여기 하나뿐
          └ image
```

반전이 회전보다 **안쪽**에 있으므로 `rotate: 175`는 반전 여부와 무관하게 항상 같은
방향으로 돈다. 각도를 뒤집는 보정이 필요 없다.

반대로 반전을 바깥에 두면 안쪽 회전이 전부 거울상이 되어, 저작한 각도와 화면이
어긋난다. 이 실수는 각도를 아무리 고쳐도 안 잡히는 종류다.

### 규칙 2 — 부위 좌표는 해석 시점에 뒤집는다

부위는 원본 기준으로 적혀 있고, 반전 레이어는 그보다 안쪽에 있다. 따라서 `pose`
레이어에서 부위를 가리키려면 x를 뒤집어야 한다.

```js
resolvePart(name, facing) {
  const p = parts[name];
  return { x: facing < 0 ? 100 - p.x : p.x, y: p.y };
}
```

`pivot: 'part:tail.base'`는 반전 시 자동으로 `100 - 74 = 26%`가 된다. 저작자는
이걸 신경 쓰지 않는다. **좌우 두 벌을 적는 일이 없어진다.**

좌/우가 이름에 든 부위(`front-leg-left`)는 뒤집을 때 짝과 교환한다. `left`가
화면 왼쪽을 뜻하는지 몬스터 기준 왼쪽을 뜻하는지 흔들리므로, **이름은 몬스터 기준으로
고정하고** 화면 기준이 필요하면 `part:front-leg.screen-left`로 요청한다.

### 규칙 3 — 방향은 앵커가 정하고, 반전은 그 결과를 따른다

이동 방향을 `facing`으로 계산하지 않는다. `to: 'hunter:2'`처럼 목적지를 적으면
런타임이 방향을 구하고, 그 방향에서 `facing`을 **파생**시킨다.

```
facing = sign(목적지.x - 현재.x)     // 이동 방향을 본다
```

지금은 반대로 하고 있다. 저작 데이터가 `facing`을 정하고 좌표도 따로 정하니 둘이
어긋나면 "돌진 방향과 머리 방향이 다르다"가 된다(레이아 연속돌진에서 실제로 났고
아직 미해결이다). 방향을 한 곳에서만 만들면 어긋날 수 없다.

## 검증

세 규칙은 눈이 아니라 테스트로 지킨다.

- 모든 `pose`의 `pivot`이 존재하는 부위를 가리키는가
- `region`을 요구하는 동작(`part` 지정)이 `region` 있는 부위만 쓰는가
- `scaleX`가 `facing` 레이어 밖에서 쓰이지 않는가
- 같은 패턴을 `facing = +1`과 `-1`로 컴파일했을 때, 부위 앵커의 **화면 좌표가 서로
  거울상인가**. 이게 반전 회귀를 잡는 핵심 검사다. 각도·축·좌표 중 하나라도 보정을
  빠뜨리면 거울 대칭이 깨진다.

## 부위 파괴와의 연결

이미 `brokenPartDamageModifiers`, `originPart`, `forbiddenWhenBroken`이 부위 이름을
쓰고 있다. 같은 이름 공간을 그대로 쓴다. 그러면 부위가 파괴됐을 때

- 그 부위를 쓰는 패턴을 선택에서 빼거나 위력을 낮추고(이미 동작)
- 그 부위의 `region` 레이어에 파손 표현을 입히고
- 그 부위 점 앵커에 이펙트를 붙이는 것

이 전부 한 데이터에서 나온다. 지금은 이름만 공유하고 그림은 따로 논다.

## 지금 필요한 것

부위 좌표는 제가 추측하면 또 틀린다. 몬스터마다 아래 표만 채워주시면 된다.
**뒤집지 않은 원본 이미지 기준, 가로·세로 퍼센트**다.

| 부위 | x% | y% | region 필요 |
|---|---|---|---|
| 머리 | | | |
| 눈(좌·우) | | | |
| 앞발(좌·우) | | | |
| 날개 | | | |
| 꼬리 밑동 | | | |
| 꼬리 끝 | | | |

`region`은 "그 부위만 따로 움직이는 공격이 있는가"로 판단한다. 나르가는 꼬리만
해당한다.

# 구현에 들어가기 전에 확정해야 하는 것들

앞의 내용은 방향이다. 그대로 코드를 짜기 시작하면 아래에서 막힌다.
각 항목은 "정하지 않으면 구현자가 임의로 정해버리고, 그 임의 선택이 다음 사고가
되는" 지점이다.

## 1. 비트는 어느 표적을 가리키는가

앞에서 `to: 'hunter:2'`라고 썼는데, **저작 시점에는 2번이 맞을지 알 수 없다.**
표적은 런타임이 `resolveTargeting`으로 고른다. 그래서 비트는 슬롯을 가리켜야 한다.

```js
'target:1'        이 패턴의 1번째 표적(패스 1)
'target:2'        2번째 표적
'target:primary'  주 표적
'target:1.left'   1번째 표적의 왼쪽 이웃
```

패턴이 `targeting: { mode, passCount }`로 표적을 고르면, 컴파일러가 그 결과를
슬롯에 채운 뒤 앵커를 픽셀로 해석한다. **저작 데이터에 헌터 번호가 등장하지 않는다.**

이게 없으면 지금과 같은 문제가 반복된다 — 좌표는 3번을 향하는데 판정은 1번에
들어가는 식이다. 이번 세션의 "1번을 노렸는데 우측을 때린다"가 그 부류였다.

**슬롯이 비면 그 비트는 건너뛴다.** 표적이 죽었거나 수가 모자랄 때 좌표가
`undefined`로 흘러 화면 밖으로 튀는 사고를 막는다.

## 2. 자세(pose) 어휘를 먼저 고정한다

`pose: 'crouch'`라고 썼지만 어휘를 정하지 않으면 저작자마다 다른 이름을 만든다.
**골격(rig)별로 한 벌씩** 정의하고, 패턴은 이름만 쓴다.

```js
poses: {
  idle:    { scale: [1, 1] },
  crouch:  { scale: [1.12, .84], offset: [0, 26] },   // 도약 준비
  stretch: { scale: [.86, 1.20] },                    // 도약 중
  land:    { scale: [1.24, .82] },                    // 착지 압축
  settle:  { scale: [1.06, .98] },                    // 착지 후 정착
  lunge:   { scale: [1.22, .84] },                    // 찌르기 접촉
  brace:   { scale: [1.16, .90] }                     // 버티기
}
```

이 일곱 개면 이번에 만든 나르가 15패턴이 전부 표현된다(실제 키프레임을 훑어
확인했다). 골격이 달라도 이름은 같고 수치만 다르다. **패턴 저작에서 `scale()`
숫자가 사라진다.**

회전이 붙는 자세는 축을 함께 갖는다.

```js
'spin-left':  { rotate: -375, pivot: 'part:front-leg-left',  recoil: 15 },
'tail-slam':  { rotate: 180,  pivot: 'part:tail.base', part: 'tail', stretch: 1.5 }
```

`recoil`은 관성 되감기 각도다. 지금은 패턴마다 손으로 프레임을 넣고 있다.

## 3. 앵커 해석기의 계약

반환값과 경계 처리를 못박지 않으면 구현자가 클램프를 임의로 넣는다. 그게 지금
`approachX .92`와 `standoff .88`이 서로 모르게 곱해진 원인이다.

- 반환은 **스테이지 좌표계의 픽셀** `{x, y}` 하나다. 배율을 곱하지 않는다.
- **클램프는 앵커 해석기만 한다.** 호출부는 클램프하지 않는다.
- 화면 밖 앵커(`offscreen:*`)는 클램프하지 않는다. 나가라고 지시한 것이다.
- OBS 하단 채팅 영역은 `safe-bottom` 경계로 한 곳에서 관리한다. 지금 코드에
  흩어진 `430` 상수가 여기로 모인다.
- 해석 실패(없는 헌터, 오타난 이름)는 **조용히 0을 반환하지 않고 던진다.**
  지금은 `undefined`가 `calc()`에 흘러들어 선언이 통째로 무효화되고 아무 신호가 없다.

## 4. 음향은 비트에 붙되 기존 페이즈와 이어붙인다

이미 `monster-audio-phase-standard.md`에 페이즈 슬롯이 있다
(telegraph / start / launch / travel / impact / recovery). 비트가 그 슬롯을 **대체하지
않고 지정**한다.

```js
{ beat: 'windup', ticks: 5, pose: 'crouch', audio: 'telegraph' }
{ beat: 'strike', ticks: 4, to: 'target:1', pose: 'lunge', hit: true, audio: 'impact' }
{ beat: 'recover', ticks: 30, pose: 'brace', audio: 'recovery' }
```

- 소리 시점 = 그 비트의 **시작 틱**. 지금처럼 `atTicks`를 따로 세지 않는다.
- 한 비트에 여러 소리가 필요하면 `audio: ['impact', 'roar']`.
- 슬롯이 비어 있으면 조용하다(`overrideOnly` 정책 그대로).

이러면 "음성이 휘두르는 중에 나온다" 같은 어긋남이 구조적으로 안 생긴다.
서머솔트 VO를 준비 자세로 옮기느라 했던 작업이 저작 한 줄로 끝난다.

## 5. 타이밍 계획서와의 관계

`monster-timing-unification-plan.md`는 **틱이 유일한 화폐**이고 배속은 틱 수만
바꾼다고 정했다. 이 문서는 그 위에 얹힌다.

- 틱 배분·배속·점유 시간 = 타이밍 계획서 담당
- 그 틱을 어떤 그림으로 채우는가 = 이 문서 담당
- 비트의 `ticks` 합 = 패턴의 활성 틱. **두 문서가 같은 숫자를 가리킨다.**

이 문서가 타이밍 계획서의 Phase 2를 흡수한다. 애니메이션 길이를 틱에서 파생시키는
작업이 곧 비트 컴파일러이기 때문이다. 계획서를 따로 구현할 필요가 없다.

## 6. 200마리를 담을 파일 구조

지금 `hunt-runtime.css` 7,700줄에 68개 모션이 섞여 있다. 200마리면 유지가 불가능하다.

```
data/hunt/monsters/<id>.js      부위 좌표 · 자세 수치 · 패턴 비트
styles/hunt-core.css            레이어 · 공용 이펙트 (모션 키프레임 없음)
```

**비트 방식에서는 몬스터별 CSS가 아예 없다.** 키프레임을 런타임이 만들기 때문이다.
`hunt-runtime.css`는 이전이 끝나는 만큼 줄어들고, 최종적으로 모션 키프레임 68개가
전부 사라진다. 이게 이 설계의 가장 큰 이득이다.

## 7. 검수 페이지가 저작 도구가 된다

지금 랩은 "재생만" 한다. 그래서 숫자를 말로 주고받는다.

비트 구조에서는 랩이 다음을 할 수 있다.

- 비트 목록을 표로 띄우고 틱·앵커·자세를 그 자리에서 바꾸기
- 앵커를 화면에 점으로 찍어 보여주기 (`target:1.bottom`이 어디인지 눈으로 확인)
- 부위 앵커를 드래그해서 좌표 잡기 → **부위 좌표를 사람이 불러줄 필요가 없어진다**
- 바꾼 결과를 `data/hunt/monsters/<id>.js` 조각으로 내보내기

**이게 토큰을 가장 크게 줄이는 지점이다.** 지금은 좌표 하나 맞추는 데 왕복 3회를
쓴다. 랩에서 직접 집으면 0회다.

## 8. 이전이 끝났다고 판정하는 기준

단계마다 "됐다"의 정의가 없으면 어중간한 상태로 쌓인다.

| 단계 | 완료 기준 |
|---|---|
| 1 앵커 해석기 | 기존 좌표 계산이 전부 해석기를 거치고, 배율·클램프가 다른 파일에 남아 있지 않다 |
| 2 레이어 분리 | `placement`에 `rotate`/`scale`이 한 번도 쓰이지 않는다(테스트) |
| 3 비트 컴파일러 | 나르가 패턴 1개가 비트로 재현되고, 접촉 틱이 기존과 일치한다 |
| 4 나르가 이전 | 15패턴 전부 비트. 나르가 전용 키프레임 0개 |
| 5 전체 이전 | `monster-motion-*` 키프레임 0개 |

각 기준은 테스트로 표현 가능하다. 사람이 화면을 보고 판정하지 않는다.

## 9. 아직 안 정한 것 (다음 논의)

- **부위 `region`을 누가 그리는가.** 랩에 폴리곤 편집기를 넣을지, 아니면 부위별
  이미지를 따로 받을지. 후자가 그림은 깨끗하지만 200마리 x 5부위 = 1,000장이 필요하다.
- **기존 68개 키프레임을 자세 프리셋으로 자동 추출할 수 있는가.** 가능하면 이전
  비용이 크게 준다. 불가능하면 몬스터마다 자세를 다시 잡아야 한다.
- **소형 몬스터 무리**(`hunt-small-monster-pack`)에 같은 구조를 쓸지. 개체가 여럿이라
  앵커 해석이 다르다.

# 자세(pose) 프리셋 상세

## 자세란 무엇인가

자세는 **이름 붙은 "그 순간의 몸 모양"** 이다. 위치는 들어가지 않는다.
위치는 비트의 `to`/`at`이 정하고, 자세는 그 위치에서 몸이 어떻게 생겼는지만 정한다.

이 분리가 핵심이다. 지금은 `scale(1.12,.84)`가 패턴마다 흩어져 있어서, "웅크림을
조금 더 깊게"를 하려면 68개 키프레임을 다 뒤져야 한다. 자세로 묶으면 한 줄이다.

## 자세가 갖는 것

```js
{
  scale:  [x, y],        // 가로·세로 배율. 기본 [1, 1]
  offset: [x, y],        // 자세 자체의 미세 이동(px). 웅크릴 때 살짝 내려앉는 등
  rotate: deg,           // 회전각. 없으면 0
  pivot:  'part:...',    // 회전·신축의 기준점. 없으면 몸 밑동
  recoil: deg,           // 접촉 후 되감기는 각도(관성). 없으면 0
  filter: '...',         // brightness/drop-shadow 등 강조
  hold:   true           // 이 자세로 멈춘다(같은 값 두 프레임을 자동 생성)
}
```

`hold`가 있는 이유는, 지금 손으로 "같은 값을 두 프레임 적어 정지를 만드는" 일을
반복하고 있기 때문이다. 그게 "휙! 착지!"의 정지를 만든다.

## 기본 일곱 자세

나르가 15패턴의 키프레임을 전부 훑어 실제로 쓰인 몸 모양을 세어보니 일곱 가지로
수렴한다. 골격이 달라도 **역할은 같고 수치만 다르다.**

### `idle` — 평상시

```js
idle: { scale: [1, 1] }
```

기준점. 모든 패턴의 시작과 끝이다. 복귀 프레임이 이 자세로 끝나면 이미지가
항상 똑바로 선다(이번에 "복귀하며 늘 원래 방향으로" 요청했던 것이 자동 보장된다).

### `crouch` — 웅크림 (도약 준비)

```js
crouch: { scale: [1.12, .84], offset: [0, 26], hold: true }
```

가로로 퍼지고 세로로 눌린다. 아래로 살짝 내려앉는다. **스프링을 압축하는 순간**이다.
`hold`가 붙어 있어 저작자가 정지 프레임을 따로 적지 않는다.

이 자세가 빠지면 도약이 "튀어오르는" 대신 "미끄러지는" 것으로 보인다. 3연 급습
2·3타가 어색했던 원인이 정확히 이것이었다.

### `stretch` — 뻗음 (도약 중)

```js
stretch: { scale: [.86, 1.20] }
```

`crouch`의 반대. 세로로 길어지고 가로로 좁아진다. 공중에 뜬 구간에 쓴다.
`crouch → stretch`가 붙어야 스프링이 풀리는 느낌이 난다.

### `land` — 착지 압축

```js
land: { scale: [1.24, .82], filter: 'brightness(1.4)' }
```

`crouch`보다 강하게 눌린다. 충격이 실린 순간이라 밝기가 올라간다.
**타격 비트(`hit: true`)는 거의 항상 이 계열이다.**

### `settle` — 정착

```js
settle: { scale: [1.06, .98], hold: true }
```

`land` 직후 몸이 제 모양으로 돌아오는 중간값. `land → settle`은 착지의 반동이다.
`hold`가 붙어 "치고 멈춤"을 만든다.

### `lunge` — 찌르기 접촉

```js
lunge: { scale: [1.22, .84], filter: 'brightness(1.5)' }
```

`land`와 비슷하지만 **앞으로 파고드는** 접촉이다. 급습·물어뜯기처럼 수평으로
파고드는 공격에 쓴다. 내려찍기는 `land` 계열, 파고드는 것은 `lunge` 계열.

### `brace` — 버티기

```js
brace: { scale: [1.16, .90], hold: true }
```

후딜 구간. 꼬리가 박힌 채 버티거나 숨을 고르는 구간이다. 3초 후딜이 이 자세로
채워진다.

## 회전이 붙는 자세

회전은 별도 자세로 만든다. 축과 되감기가 함께 따라다녀야 하기 때문이다.

```js
'spin-left':  { rotate: -375, pivot: 'part:front-leg-left',  recoil: 15, scale: [1.06, 1] },
'spin-right': { rotate:  375, pivot: 'part:front-leg-right', recoil: 15, scale: [1.06, 1] },
'tail-slam':  { rotate:  180, pivot: 'part:tail.base', scale: [1.10, 1.52],
                filter: 'brightness(1.48) drop-shadow(0 14px 20px #000a)' },
'tail-whip':  { rotate: -175, pivot: 'part:body.base', windup: 22, recoil: 15 }
```

- `rotate` 375 = 한 바퀴 + 15도. **관성이 실리는 오버슛**이다.
- `recoil` 15 = 접촉 후 15도 되감긴다. 오버슛과 짝이다.
- `windup` 22 = 회전 **반대 방향으로** 22도 감았다가 푼다. 반동이다.

이 세 값이 자세에 들어있으므로, 패턴은 `pose: 'tail-whip'` 한 줄만 쓴다.
지금은 반동·오버슛·되감기를 패턴마다 프레임으로 손으로 넣고 있고, 그래서
역회전 연계의 두 회전 속도가 4.1배 차이 나는 것 같은 사고가 났다.

## 비트와 자세가 만나면

컴파일러는 비트마다 `(위치, 자세)` 쌍을 만들고 그 사이를 보간한다.

```js
{ beat: 'windup', ticks: 5, pose: 'crouch' }
{ beat: 'leap',   ticks: 3, to: 'target:1', pose: 'stretch' }
{ beat: 'strike', ticks: 4, to: 'target:1.bottom', pose: 'land', hit: true }
{ beat: 'hold',   ticks: 2, pose: 'settle' }
```

이 네 줄에서 자동으로 나오는 것:

- **키프레임 8개** (`hold: true`인 자세는 두 프레임으로 펼쳐진다)
- **총 14틱** = 1400ms
- **접촉 시점** = 8틱 지점 (`strike` 비트 시작)
- **회전축·되감기** = 자세가 들고 있다

지금 이 정도를 손으로 쓰면 키프레임 12~15줄에 숫자 30개다.

## 골격별로 수치만 바꾼다

이름은 고정이고 값은 골격마다 다르다.

```js
rigs: {
  winged:    { crouch: { scale: [1.12, .84], offset: [0, 26] }, ... },
  quadruped: { crouch: { scale: [1.16, .80], offset: [0, 20] }, ... },
  serpentine:{ crouch: { scale: [1.04, .92], offset: [0, 14] }, ... }
}
```

새 몬스터를 넣을 때 **자세를 새로 정의하지 않는다.** 골격만 고르면 일곱 자세가
따라온다. 특별한 기술이 있으면 그 몬스터에만 자세 하나를 추가한다.

이게 200마리를 감당하는 방식이다. 마리당 새로 적는 것은 부위 좌표 6개와
패턴별 비트 몇 줄뿐이다.

## 검증

- 패턴이 참조하는 자세 이름이 전부 존재하는가
- 회전 자세의 `pivot`이 존재하는 부위를 가리키는가
- 같은 역할의 자세가 골격마다 전부 정의되어 있는가(빠지면 `idle`로 떨어져 밋밋해진다)
- `hold`가 붙은 자세가 실제로 두 프레임으로 펼쳐지는가

# 자동 추출 실측 결과

기존 68개 키프레임에서 자세를 자동으로 뽑을 수 있는지 실제로 돌려봤다. **가능하다.**
그리고 그 과정에서 앞 절의 설계 오류가 드러났다.

## 설계 오류 — scale은 한 축이 아니라 두 축이다

앞에서 자세를 `scale: [x, y]`로 정의했다. 틀렸다. 실측하면 `scale`에는 성격이
다른 두 가지가 섞여 있다.

| 축 | 의미 | 계산 |
|---|---|---|
| **자세** | 스쿼시/스트레치 | 비율 `r = x / y` |
| **원근** | 몬스터가 가깝거나 멀다 | 크기 `s = sqrt(x * y)` |

515개 프레임 중 **320개(62%)가 비율 1.000**이다. 즉 자세는 없고 **원근만** 있다.
그리고 그 320개의 원근 값은 **0.52 ~ 1.62로 3.1배** 퍼져 있다.

이 둘을 한 필드에 묶으면 같은 "웅크림"인데 거리가 다르다는 이유로 매번 다른 숫자를
적게 된다. 지금 키프레임에 `scale` 조합이 **139가지**나 있는 이유가 이것이다.
분리하면 자세는 13가지로 줄어든다.

**따라서 자세에서 `scale`을 빼고 비율만 둔다. 원근은 비트가 갖는다.**

```js
// 자세 — 몸 모양만
crouch: { squash: 1.294, hold: true }     // 가로/세로 비율
stretch: { squash: 0.744 }

// 비트 — 위치와 거리
{ beat: 'strike', ticks: 4, to: 'target:1.bottom', pose: 'land', depth: 1.18, hit: true }
```

`depth`는 앵커에서 자동으로 나올 수도 있다. 헌터에게 다가갈수록 커지는 값이므로,
`to`가 정해지면 컴파일러가 기본값을 계산하고 필요할 때만 저작자가 덮는다.
**그러면 원근 숫자도 대부분 사라진다.**

## 자세 일곱 개로 몇 %가 덮이는가

비율만으로 군집화하면 13개가 나오고, 상위 7개가 **93.2%**를 덮는다.

| 자세 | 비율 | 프레임 수 |
|---|---|---|
| `idle` | 1.000 | 320 |
| `stretch` | 0.744 | 51 |
| `crouch` | 1.294 | 42 |
| `settle` | 1.090 | 35 |
| `land` | 1.430 | 32 |
| `stretch-soft` | 0.923 | 26 |
| `stretch-strong` | 0.655 | 9 |

앞 절에서 이름으로 추측했던 일곱 개와 **역할이 거의 일치한다**(`lunge`는 `land`와
비율이 겹쳐 하나로 합쳐지고, 대신 `stretch`가 세 단계로 갈린다). 이름은
실측값에 맞춰 고친다.

## 스냅 오차

모든 프레임을 이 일곱 비율로 스냅했을 때:

- **평균 오차 0.56%**
- 최대 오차 9.70%
- **오차 5% 초과: 515개 중 10개 (1.9%)**

평균 0.56%는 화면에서 구분이 안 되는 수준이다. **자동 이전이 안전하다.**

5%를 넘는 10개는 모션 이름이 특정된다.

```
bazel-carpet-bombing, leap-slam, nargacuga-flank-charge,
nargacuga-offscreen-charge, nargacuga-bite-spin-return, nargacuga-lunge-finish
```

이 여섯 모션만 사람이 보고 전용 자세를 줄지 스냅을 받아들일지 판단하면 된다.
**68개 중 6개다.**

## 결론

- 자동 추출 **가능**. 이전 비용의 대부분이 사라진다.
- 추출기가 만드는 것: 자세 프리셋 표 + 패턴별 비트 초안(자세 이름과 틱).
- 사람이 하는 것: 앵커 이름 지정(좌표는 이미 있는 것을 매핑), 예외 6개 검토.
- **설계는 `scale`을 `squash`(자세)와 `depth`(비트)로 쪼개는 쪽으로 수정한다.**

이 추출기는 일회용이 아니다. 이전이 끝난 뒤에도 "새로 만든 비트가 기존 그림과
같은가"를 비교하는 회귀 검사로 쓴다. 4단계(나르가 이전)의 완료 판정이 그 비교다.

# 1단계 결과 — 앵커 해석기

`js/effects/hunt/HuntStageAnchors.js`. 계약은 위 "3. 앵커 해석기의 계약" 그대로다.

## 구현한 어휘

```
home / self                     원점
hunter:2                        2번 헌터 중심
hunter:2.bottom                 .top .left .right .center
between:1,2                     여럿의 중점
arena:center / arena:center-lower [비율]
toward:hunter:2 92%             홈에서 목적지까지의 92% 지점
above|below|left|right:<앵커> 150
polar:hunter:2 225deg 320       0도가 위, 시계 방향
offscreen:left|right|top|bottom [여백]
```

반환은 홈(정지 중심) 기준 픽셀 오프셋이다. 그대로 `translate()`에 넣을 수 있고,
기존 `--monster-attack-x/y`와 같은 공간이라 병존이 가능하다.

## 문법으로 막은 것

**배율 중첩을 금지했다.** `toward:toward:hunter:1 92% 88%`는 예외를 던진다.
인자를 받는 연산자를 중첩하면 인자가 어느 쪽 것인지 문법으로 구분되지 않고,
안쪽이 조용히 기본값을 쓴다. `.92 * .88 = .81` 사고가 바로 그 모양이었다 —
두 배율이 서로 모르게 곱해져 표적까지의 81%에서 멈췄다. 신호 없는 오답 대신
예외를 낸다.

**빈 인자를 0으로 읽지 않는다.** `polar:hunter:2 225deg`(거리 누락)는 예외다.
`Number('')`은 0이므로, 막지 않으면 인자를 빠뜨린 앵커가 조용히 원점으로 해석된다.

## 경계는 세 벌뿐이다

| 프리셋 | 세로 | 가로 | 쓰임 |
|---|---|---|---|
| `contact` | -240 ~ 430 | ±lane | 접촉 기술 |
| `standoff` | -190 ~ 8 | ±lane | 서서 쏘는 기술 |
| `pivot` | -240 ~ 430 | ±960 | 회전 기술 |

`430`(OBS 채팅 안전선)의 유일한 출처가 여기다. 예전에는 애니메이터·급습·글라이드·
양탄자폭격 네 곳에 복사돼 있었다. 클램프는 상대 이동을 **다 적용한 뒤 마지막에
한 번만** 걸린다 — 중간에 걸리면 "위로 150" 지시가 안전선에 먼저 눌려 사라진다.

`pivot`이 가로를 넓게 여는 이유는, 회전 기술은 표적 바로 위에 자리를 잡는 것이 곧
공격이기 때문이다. 이동 한계로 끌어당기면 축이 헌터에서 벗어나 꼬리가 닿지 않는다.

## 구현 중에 드러난 실제 버그

**헌터 번호는 0부터다.** 처음에 `fight-card-1`부터 4까지 훑도록 썼는데, 실제
DOM은 `fight-card-0`부터다. 0번을 놓치고 없는 4번을 지어냈다. 패턴 랩에서 바로
드러났다. 지금은 번호를 세지 않고 `[id^="fight-card-"]`로 **발견한다** — 인원수가
바뀌어도 따라간다.

이 종류가 정확히 재설계가 겨냥한 실패다. 범위를 가정한 코드는 조용히 틀리고,
발견하는 코드는 틀릴 자리가 없다.

## 계측 — 클램프가 실제로 무는가

1920x1080 실제 레이아웃에서:

```
lane(maxX)        600
헌터까지 dx       -662  -238  +186  +610
```

바깥 두 명이 lane을 넘는다. 접근 배율 `.92`를 곱하면 0번은 -609 → -600으로
**9px 잘리고**, 3번은 561로 안 잘린다. 클램프가 무는 양은 크지 않다 —
"돌진이 헌터 앞에서 멈춘다"의 원인은 여기가 아니라는 뜻이다.

## 검증

`tests/hunt-stage-anchors.test.js`. 어휘·경계·예외를 고정하는 것 외에,
**상수가 다시 복사되는 것을 소스 검사로 막는다.**

```

  Math.min(430 / Math.max(-240 / (stage?.clientWidth || 720) 이 다시 나타나면 실패
```

해석기 자신은 상수를 가져야 하므로 `SAFE_BOTTOM = 430`이 있는지도 함께 본다.
이게 없으면 "지워서 통과"가 가능해진다.

패턴 랩에서 나르가 15패턴을 전부 재생해 콘솔 오류 0, 좌표 회귀 없음을 확인했다.

# 2단계 결과 — 레이어 분리

```
.hunt-monster-attack-motion   placement  translate 전용 (옛 키프레임 68개가 여기 그대로)
  .hunt-monster-pose-layer    pose       rotate/scale 전용  ← 새로 넣은 것
    .hunt-monster-aim-layer   aim        대상을 바라보는 몸 방향
      .hunt-monster-facing-layer  facing scaleX(±1) — 반전은 여기 하나뿐
        img
```

## 옛 경로를 건드리지 않는다

자세 레이어의 기본값이 항등(`rotate(0deg) scale(1,1)`)이라, 지금 동작하는 68개
키프레임은 아무 영향을 받지 않는다. 실제로 패턴 랩에서 나르가 15패턴을 전수
재생해 확인했다 — 콘솔 오류 0, 좌표 회귀 없음. `getComputedStyle`로 읽은 자세
레이어 변환도 `matrix(1,0,0,1,0,0)`이다.

이게 병존 전략의 요점이다. 3단계에서 새 경로를 만들 때 옛 경로를 끄지 않아도 된다.

## 자세는 비율과 원근의 곱이다

`HuntMonsterAttackAnimator.poseScale(squash, depth)`:

```
scaleX = depth * sqrt(squash)
scaleY = depth / sqrt(squash)
  => scaleX / scaleY        = squash   (자세)
     sqrt(scaleX * scaleY)  = depth    (원근)
```

왕복이 성립하므로 기존 키프레임에서 뽑은 비율/원근을 그대로 넣을 수 있다.
잘못된 값(0, 음수, NaN, 문자열)은 1로 떨어진다 — CSS는 오류를 내지 않으므로
NaN이 흘러들면 `scale()`이 통째로 무효화되고 "아무 일도 안 일어남"으로만 보인다.

## 회전축은 CSS가 아니라 데이터다

`applyPose`는 `pivot: 'part:tail'`을 받아 `HuntStageAnchors.resolvePart`로 풀고,
결과를 `--pose-pivot-x/y`에 쓴다. **CSS `transform-origin`을 직접 쓰지 않으므로
특이도 사고가 원천적으로 발생하지 않는다.** rig 기본 축이 모션별 축을 이기던
22개 규칙 같은 일이 축을 데이터로 옮기면 성립하지 않는다.

반전도 여기서 자동으로 풀린다. 실측(패턴 랩, 이미지 380px):

```
facing = +1   축 114px
facing = -1   축 266px      114 + 266 = 380 → 정확한 거울상
회전 행렬은 두 경우가 완전히 동일   ← 반전이 회전보다 안쪽이라 각도가 안 뒤집힌다
```

저작자는 좌우 두 벌을 적지 않는다.

## 검증

`tests/hunt-monster-layer-contract.test.js`:

- **마크업 5곳을 대조한다** — 실수렵(HuntRenderer)과 패턴 랩, 프리뷰 3종의
  레이어 순서가 같은지. 검수 화면과 실제 화면이 갈라지면 "여기서 고친 게 저기서
  안 보인다"가 되고, 이번 세션에서 그 오해에 검수 두 라운드를 썼다.
- **반전이 facing 레이어 바깥에 있으면 실패시킨다** — CSS에서 몬스터 레이어에
  `scaleX`를 거는 규칙을 전수로 훑는다. 바깥에 걸면 안쪽 회전이 전부 거울상이
  되고, 각도를 아무리 고쳐도 안 잡히는 종류의 사고가 난다.
- **자세 레이어에 `translate`가 있으면 실패시킨다** — 이동은 placement의 것이다.
- 자세 분해의 왕복과 잘못된 값의 안전 처리.

레이어 순서를 정규식으로 겹쳐 적던 기존 두 테스트(패턴 랩, 비룡 프리뷰)는 이 대조로
합쳤다. 두 곳에 적어두면 레이어가 늘 때마다 둘 다 고쳐야 하고, 한쪽을 잊으면 정확히
막으려던 divergence가 다시 생긴다.
